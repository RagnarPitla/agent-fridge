# Adapters

How `fridge adapters install` puts one canonical block of rules into your agent's instruction file, and keeps it current.

An agent participates in Agent Fridge Board by running a command and reading an exit
code. It has to be told to do that. Adapters are how: one short, canonical rule
text, spliced into whichever vendor instruction files your repository already
uses, with a hash so drift is detectable.

Hooks are covered at the end. **Hooks are an upgrade, never a requirement.**
An agent that can only read repository instructions and run a shell command can
take part fully. That is a design constraint of the protocol, not an accident
([../spec/protocol-v0.1.md](../spec/protocol-v0.1.md#13-design-constraints),
constraint 7).

---

## The commands

```bash
fridge adapters install                        # every vendor file, present or not
fridge adapters install --vendor claude        # one vendor
fridge adapters install --vendor claude,copilot,codex
fridge adapters check                          # exit 30 if anything is missing or stale
fridge adapters list                           # per-vendor state, no writes
fridge adapters print                          # print the canonical block, no writes
```

`install` is the default subcommand, so bare `fridge adapters` installs.

`fridge init` runs the equivalent of `fridge adapters install --vendor agents`
for you, so a fresh workspace already has the block in `AGENTS.md`. Pass
`fridge init --no-adapters` to skip that.

---

## The vendor files it targets

These are the exact paths, from `src/adapters/templates.mjs`:

| Vendor key | File | Who reads it |
| --- | --- | --- |
| `agents` | `AGENTS.md` | Codex, Copilot CLI, Amp, and anything that reads `AGENTS.md` |
| `claude` | `CLAUDE.md` | Claude Code |
| `copilot` | `.github/copilot-instructions.md` | GitHub Copilot, IDE and CLI |
| `codex` | `.codex/instructions.md` | OpenAI Codex, explicit file |
| `cursor` | `.cursor/rules/agent-fridge.mdc` | Cursor |
| `generic` | `docs/AGENT-COORDINATION.md` | Any other tool, and humans |

`--vendor all` is accepted and is the same as passing no `--vendor` at all.
Parent directories are created as needed.

### Seeing the current state

```bash
fridge adapters list
```

```
agents   current   AGENTS.md
claude   missing   CLAUDE.md
copilot  missing   .github/copilot-instructions.md
codex    missing   .codex/instructions.md
cursor   missing   .cursor/rules/agent-fridge.mdc
generic  missing   docs/AGENT-COORDINATION.md
```

Four states:

| State | Meaning |
| --- | --- |
| `missing` | The file does not exist |
| `absent` | The file exists but has no block |
| `drifted` | The file has a block whose hash is not the current one |
| `current` | The file has the current block |

## The canonical block, verbatim

There is exactly one rule text. Every vendor file gets the same one, which is
why there is one source of truth and why drift is a yes-or-no question.

```bash
fridge adapters print
```

<!-- The block below is quoted output, not an installed block. -->

````markdown
<!-- BEGIN WCP-ADAPTER v0.1 hash:b33f7caedcfc -->
<!-- Generated by `fridge adapters install`. Edit the protocol, not this block. -->
## Shared fridge: how we avoid erasing each other

This repository may have more than one agent or human working in it at the same time.
The fridge door is the shared board. Everybody pins their own note. Nobody edits anybody
else's note. State lives in `.fridge/`; `.fridge/DOOR.md` is a generated view, never edit it.

Before you edit files:

```sh
fridge join --agent "<your-name>" --vendor "<claude|copilot|codex|human|other>"   # once per session
fridge claim "<path-or-glob>" --task "<what you are doing>" --ttl 30m            # take the chore
```

If `fridge claim` exits **10**, somebody else already has that chore. Do not edit those paths.
Read `fridge board`, then either claim different paths, `fridge wait <claim-id>`, or ask via
`fridge handoff <claim-id> --to <them> --note "..."`. Never work around a conflict by editing anyway.

While you work:

```sh
fridge check <path>...            # exit 0 mine, 10 theirs, 14 unclaimed
fridge heartbeat                  # "still on it" - renews your lease
fridge pin "what just happened"   # durable note, write-once, never overwrites anyone
fridge release <claim-id> --outcome done --note "what changed"
```

Rules:

1. Do not hand-edit anything under `.fridge/` and do not edit `.fridge/DOOR.md`.
2. Do not use `--force` to take somebody else's card unless a human told you to.
3. Claim the narrowest paths that cover your work, and release when you stop.
4. Report progress with `fridge pin`, not by editing a shared Markdown file.

Full protocol: `.fridge/` and https://github.com/RagnarPitla/agent-fridge (protocol wcp/0.1).
<!-- END WCP-ADAPTER v0.1 -->
````

It is about 30 lines on purpose. Agents that read 25 lines follow 25 lines. It
does not restate the documentation; it states the four things an agent must do
and points at `fridge --help` and the protocol for everything else.

## How the splice works

### Marker-delimited, with a content hash

The block is delimited by:

```
<!-- BEGIN WCP-ADAPTER v0.1 hash:b33f7caedcfc -->
...
<!-- END WCP-ADAPTER v0.1 -->
```

`hash:` is a short hash of the rule text itself. That is the whole drift
mechanism: an installed block whose hash matches the current rule text is
`current`; anything else is `drifted`.

### Your own text survives

`install` never rewrites a file wholesale. It does one of three things:

| Situation | What happens | Reported as |
| --- | --- | --- |
| File does not exist | Create it containing just the block | `created` |
| File exists, no block | Append the block, leave every existing byte alone | `appended` |
| File exists, has a block | Replace the bytes between the markers only | `updated` |
| File exists, block is current | Do nothing at all | `unchanged` |

So this is safe:

```markdown
# CLAUDE.md

Project-specific instructions I wrote by hand.
Please always run `npm run lint` before committing.

<!-- BEGIN WCP-ADAPTER v0.1 hash:b33f7caedcfc -->
...generated...
<!-- END WCP-ADAPTER v0.1 -->

More of my own notes, below the block.
```

Re-running `install` rewrites only the middle. The prose above and below is
untouched, byte for byte.

The one thing that will stop it is a start marker with no matching end marker.
That is unrecoverable automatically, so it fails loudly with `E_STATE_CORRUPT`
and tells you to delete the partial block by hand.

### Idempotent

```bash
fridge adapters install
```

```
ok      AGENTS.md  (unchanged)
missing CLAUDE.md  (created)
missing .github/copilot-instructions.md  (created)
missing .codex/instructions.md  (created)
missing .cursor/rules/agent-fridge.mdc  (created)
missing docs/AGENT-COORDINATION.md  (created)
```

The first column is the state before the run; the parenthesised word is what was
done. Run it again and everything says `unchanged`:

```bash
fridge adapters install --vendor claude
```

```
ok      CLAUDE.md  (unchanged)
```

Files are written with an atomic staged rename, so an interrupted install leaves
either the old file or the new one, never a truncated one.

### Drift detection

`fridge adapters check` writes nothing and exits `30` (`E_DRIFT`) if any vendor
file is missing, absent, or drifted:

```bash
fridge adapters check --vendor claude
```

```
drifted CLAUDE.md
E_DRIFT: 1 instruction file(s) are missing or out of date.
hint: fridge adapters install
```

`fridge doctor` reports the same thing as a warning, and `fridge doctor --fix`
reinstalls:

```
WARN   CLAUDE.md has an out-of-date instruction block.  (fridge adapters install)
```

```
FIXED  CLAUDE.md has an out-of-date instruction block.
```

Add `fridge adapters check` to CI to keep a repository honest after a
Agent Fridge Board upgrade. See [./interop.md](./interop.md).

## Per-vendor notes

The block is identical everywhere. What differs is where the file lives, when
the agent reads it, and what optional extras exist.

### Claude Code

```bash
fridge adapters install --vendor claude
```

Writes `CLAUDE.md` at the repository root. Claude Code reads it at session
start, so start or restart the session after installing.

Then, in the terminal running Claude Code:

```bash
fridge join --agent claude --vendor claude
export FRIDGE_ACTOR=claude
```

Give each concurrent Claude session a distinct name (`claude-a`, `claude-b`), or
they share one session and therefore one set of claims.

An optional `PreToolUse` hook that turns the advice into enforcement is in the
hooks section below.

### GitHub Copilot CLI

```bash
fridge adapters install --vendor copilot
```

Writes `.github/copilot-instructions.md`, which is read by both Copilot in the
IDE and Copilot CLI. If your repository already uses `AGENTS.md`, Copilot CLI
reads that too, so `--vendor agents,copilot` covers both.

```bash
fridge join --agent copilot --vendor copilot
export FRIDGE_ACTOR=copilot
```

Copilot CLI spawns a new process per command. That is fine and expected: the
session is resumed by name, and liveness comes from the lease, not the pid. See
[./concepts.md](./concepts.md).

### OpenAI Codex and Codex CLI

```bash
fridge adapters install --vendor agents,codex
```

`AGENTS.md` is the file most Codex setups read; `.codex/instructions.md` is the
explicit one. Installing both is cheap and covers either configuration.

```bash
fridge join --agent codex --vendor codex
export FRIDGE_ACTOR=codex
```

### Cursor

```bash
fridge adapters install --vendor cursor
```

Writes `.cursor/rules/agent-fridge.mdc`. Cursor's rules directory is read
automatically for the project.

Cursor edits files through its own UI, so the useful pattern is to have the
agent claim before a multi-file edit and check before writing:

```bash
fridge claim "src/components/**" --task "extract the Button primitive"
fridge check src/components/Button.tsx --for-write
```

```bash
fridge join --agent cursor --vendor cursor
export FRIDGE_ACTOR=cursor
```

### Any agent with shell access

If your agent is not in the list (Windsurf, Cline, Aider, Continue, an in-house
harness, a shell script, a human), it still works. Install the generic file and
point the agent at it:

```bash
fridge adapters install --vendor agents,generic
```

That writes `AGENTS.md` and `docs/AGENT-COORDINATION.md`. If the tool reads some
other file, paste this in:

```markdown
## Shared workspace coordination

Other agents and humans may be working in this checkout right now.

1. Identify yourself once per session:
   `fridge join --agent "<your-name>" --vendor other`
   then `export FRIDGE_ACTOR="<your-name>"`.
2. Before editing files, claim them:
   `fridge claim "<paths>" --task "<what you are doing>"`
   Exit 10 means somebody else has them. Do not edit anyway. Claim narrower
   paths, run `fridge wait <claim-id>`, or ask for a handoff.
3. Check a single path with `fridge check <path>`: exit 0 yours or free,
   10 theirs, 14 unclaimed with --for-write.
4. Leave durable notes with `fridge pin "..."`. Never edit a shared Markdown
   file to report progress.
5. When you stop: `fridge release <claim-id> --outcome done --note "..."`.
6. Never hand-edit anything under `.fridge/`.

Every command accepts --json and prints one JSON envelope on stdout.
Read `fridge --help` and `fridge <command> --help` for the rest.
```

The integration surface really is that small: run a command, read the exit code.

### A human being

No adapter needed. `fridge board`, or open `.fridge/DOOR.md` in an editor. Join
with `--vendor human` so the board reads correctly:

```bash
fridge join --agent ragnar --vendor human
```

## Optional: hooks

Everything above is cooperative. An agent follows the rules because it was
asked to. Hooks close the gap by refusing the write itself.

**They are optional.** Adopt them if your team wants a hard stop; skip them
entirely if you do not. Nothing in the protocol requires them, and no feature is
gated behind them.

The command they both use is `fridge guard`, which asserts that paths are
covered by claims you hold:

```bash
fridge guard src/api/routes.ts      # named paths
fridge guard --staged               # everything in the Git index
```

Exit `0` means fine, `10` means somebody else holds a path, and `14` means a
path is outside any card you hold. Whether unclaimed paths fail is controlled by
`policy.requireClaimForWrite` in `.fridge/config.json`, which defaults to
`advisory` (unclaimed is allowed). Set it to `strict` to make unclaimed paths
fail:

```bash
fridge config policy.requireClaimForWrite strict
```

### Claude Code PreToolUse hook

`PreToolUse` runs before a tool call and can reject it. Wire it to `fridge
guard` so an edit outside your claims never reaches the filesystem.

In `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit|NotebookEdit",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/fridge-guard.sh"
          }
        ]
      }
    ]
  }
}
```

`.claude/hooks/fridge-guard.sh`, marked executable with `chmod +x`:

```bash
#!/usr/bin/env bash
# Refuse an edit that is outside this agent's Agent Fridge Board claims.
# Reads the PreToolUse payload on stdin and extracts the target path.
set -uo pipefail

payload="$(cat)"
path="$(printf '%s' "$payload" | node -e '
  let s = "";
  process.stdin.on("data", (d) => { s += d; });
  process.stdin.on("end", () => {
    try {
      const i = JSON.parse(s).tool_input || {};
      process.stdout.write(i.file_path || i.path || i.notebook_path || "");
    } catch { process.stdout.write(""); }
  });
')"

[ -z "$path" ] && exit 0

export FRIDGE_ACTOR="${FRIDGE_ACTOR:-claude}"
fridge guard "$path"
case $? in
  0)  exit 0 ;;
  2)  exit 0 ;;   # usage or path outside the repo: not the hook's business
  3)  exit 0 ;;   # no .fridge/ here: nothing to enforce
  7)  exit 0 ;;   # nobody joined: do not block a repo that is not using this
  *)  echo "Agent Fridge Board: $path is not covered by a claim you hold." >&2
      echo "Run: fridge claim \"$path\" --task \"<what you are doing>\"" >&2
      exit 2 ;;   # non-zero tells Claude Code to block the tool call
esac
```

Two things to note. It exits `0` on `E_NOT_INITIALIZED` and `E_NO_SESSION`, so
the hook is harmless in a checkout that is not using Agent Fridge Board. And the hook
is per-machine configuration, not protocol: an agent on another machine without
the hook still coordinates correctly through the instruction block.

### Git pre-commit hook

The lower-effort, higher-value option. It catches the case where an agent edited
outside its claims and is now about to commit.

`.git/hooks/pre-commit`, marked executable with `chmod +x`:

```bash
#!/usr/bin/env bash
# Refuse a commit whose staged files are not covered by claims you hold.
set -uo pipefail

command -v fridge >/dev/null 2>&1 || exit 0
[ -d .fridge ] || exit 0

fridge guard --staged
code=$?
case $code in
  0) exit 0 ;;
  7) exit 0 ;;   # nobody joined in this shell; do not block a human
  *)
    echo "" >&2
    echo "Commit refused: staged files are not yours to commit (exit $code)." >&2
    echo "  fridge board          # who has them" >&2
    echo "  fridge claim ...      # take them properly" >&2
    exit 1
    ;;
esac
```

```
yours     src/api/routes.ts  (claude, clm_01M0D41839D701M6J51EBT7GFZ)
yours     src/ui/App.tsx  (claude, clm_01M0D41839D701M6J51EBT7GFZ)
```

`.git/hooks/` is not committed, so distribute it with a `core.hooksPath`
directory that is:

```bash
mkdir -p .githooks
mv .git/hooks/pre-commit .githooks/pre-commit
git config core.hooksPath .githooks
git add .githooks/pre-commit
```

You can add a second line to the same hook to catch a stale door:

```bash
fridge render --check || { echo "Run: fridge render" >&2; exit 1; }
```

### What hooks do not fix

A hook is defence in depth, not a security boundary. Any process that can run
`fridge` can also write the file directly, and a hook only covers the paths the
hook itself sees. If you need real isolation, give each agent its own checkout
with a Git worktree. [./comparison.md](./comparison.md) explains when that is
the better answer, and it often is.

## Troubleshooting

**The agent ignores the block.** Restart the agent session; most read
instruction files once at start. Then check the file is the one that agent
actually reads (`fridge adapters list` shows all six). If it still ignores it,
that is an advisory-system limitation, not a bug: add the pre-commit hook.

**`fridge adapters check` exits 30 after upgrading Agent Fridge Board.** Expected. The
rule text changed, so the hash changed. Run `fridge adapters install` and commit
the result.

**I edited the block and it keeps coming back.** That is the design. Edit your
own prose above or below the markers; the block itself is generated. If the rule
text is wrong, change it in `src/adapters/templates.mjs` and open a pull
request, so every repository gets the fix.

**A start marker with no end marker.** `E_STATE_CORRUPT`. Delete the partial
block by hand, then `fridge adapters install`.
